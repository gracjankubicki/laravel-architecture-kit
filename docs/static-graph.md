# Static application graph

The graph connects declarations and source-visible Laravel operations. Agents use it to find an entry point, inspect its relationships, follow a directed path, or identify possible dependents before editing code.

Discovery reads source files. It does not boot the inspected application, load its autoloader, evaluate its configuration, run queries, dispatch jobs, or execute tests. A relationship describes a possible source-level transition. Ordinary method calls check source visibility, effective trait alias visibility, abstract declarations and static invocation compatibility. Invalid selections remain structural references with diagnostics, without a path into the method body. Resource effects recheck facade identity and ordered namespaced/global helper candidates against the current source index, including cached callers. Its evidence identifies the file and source location; `execution_proven` remains false.

## Source scope

The default roots are `app`, `routes`, `bootstrap`, `config`, `database`, `resources/views`, and `tests`. Composer metadata identifies optional package versions. Unsafe roots, missing roots, unsupported shapes, and dynamic expressions produce diagnostics.

Additional graph roots and exclusions are static settings in `config/architectures.php`:

```php
return [
	'graph' => [
		'paths' => ['src', 'packages/Billing'],
		'exclude' => ['packages/Billing/generated/*'],
	],
];
```

`graph.paths` adds roots to the defaults. `graph.exclude` filters discovery. Audit rules retain their separately configured `audit.paths` scope. Adding a root to the graph does not enable audit rules for that root.

## Saloon source requests

The inspected Saloon contract is `saloonphp/saloon` 4.0.0 at commit `1307b1d72cacdd2c9c20978cdf7a0b720b4bf3bb`. Composer metadata must identify this version and, when present, the matching source reference. Other versions produce an unresolved-contract diagnostic.

For application classes extending Saloon `Connector` and `Request`, the graph connects `send`, `sendAsync` and `sendAndRetry` to a source-resolved external endpoint. It selects `resolveBaseUrl` and `resolveEndpoint` across source inheritance and trait aliases, reads their bounded constant return descriptors, and checks the source hash. It does not instantiate the connector, request or sender. Typed parameters, constructed requests and source-resolved receiver types use the existing call resolver.

`createPendingRequest` records an endpoint reference and selector preparation, not a transport transition. `sendAsync` remains conditional on consuming the asynchronous task. All transport candidates retain `execution_proven=false` and `traffic_proven=false`; mocks, boot hooks and middleware can change runtime behavior. Credentials, query strings, fragments and request payloads are omitted.

Request-side `send`, `sendAsync` and `createPendingRequest` use their separate optional `mockClient` signature. The graph recognizes `SoloRequest` with its default empty-base `NullConnector`, source `resolveConnector` factories, and literal connector class properties across source inheritance and traits. A private connector property requires the declaring scope to be accessible to `HasConnector`. Property selection remains a structural reference. A possible send remains conditional on the connector selection staying active; runtime `setConnector` can replace it.

Absolute endpoint selection follows source defaults for `allowBaseUrlOverride`: a non-null request value takes precedence, a null request value falls back to the connector, and `SoloRequest` defaults to true. Source inheritance and compatible trait properties retain their declaration evidence. A dynamic, inaccessible or conflicting flag remains unresolved. Runtime assignments can change these defaults; OAuth configuration for internal token and user requests requires separate inspection.

Pool source facts retain at most 128 distinct constructed member types from literal arrays and simple inline factories. They retain the factory's source identity and distinguish generator bodies from ordinary callbacks, including yields nested in branches or assignments. Nested callable bodies do not change the enclosing factory's generator status. Conditional or unmodeled factory statements remain unresolved; oversized lists report a structural limit. Constructor arguments are omitted. These facts alone do not prove a Saloon receiver or create a transport edge.

Source `Connector::pool` factories now connect literal request candidates to an assigned, aliased or chained pool's zero-argument `send`. Ordinary inline factory bodies are candidates at pool preparation; generator bodies are candidates only at pool consumption. Preparation and member references remain structural, so constructing a pool does not create a path to transport. Pool sends reuse the asynchronous endpoint resolver and preserve pool source evidence. Source pool overrides, decoy receivers, unverified versions, shadowed package classes and reassigned variables suppress the default composition. Runtime `setRequests` can replace the member list.

Direct `new Pool` uses its separate constructor signature, including named `connector` and `requests` arguments. The graph resolves the source connector type and follows the constructed pool's instance identity to `send`. Source subclasses require an inherited standard constructor and standard `send`, `setRequests`, `setConcurrency`, `withResponseHandler` and `withExceptionHandler`; source overrides remain unresolved. Constructor candidates for unrelated classes never become Saloon transport edges.

Source `setRequests` replaces the pool member candidates within the current callable. Aliases share the pool's instance identity, and a setter's returned pool preserves that identity through a chain. A setter inside a branch, loop, conditional expression or nullsafe call retains the previous list as an alternative. Ordinary replacement factories are invocation candidates when the setter runs; replacement generators are consumed by `send`. Dynamic replacement lists suppress obsolete unconditional members and report incomplete selection. Pool sites use both start and end offsets, since nested calls in one chain can share their start offset. Selection is bounded to 128 branch candidates.

Inline response, exception and concurrency callbacks are selected from `pool` arguments, `new Pool` arguments, or the fluent `withResponseHandler`, `withExceptionHandler` and `setConcurrency` methods. Registration is structural. A pool's `send` links to the selected response handler only conditionally on promise fulfilment, to its exception handler on rejection, and to its concurrency handler when iteration requests a concurrency value. Setter aliases retain pool identity, later setters replace the chosen handler, and `setRequests` preserves handlers. Conditional setters retain alternative selections. Known empty member lists do not invoke response or exception handlers. Generator handlers are unresolved because the pool does not consume their returned generator. Handlers can also come from variables, aliases, first-class method references, source callable arrays, invokable objects and source factories returning these values. Source visibility and static binding are checked, including private first-class methods captured in their declaring scope. Factory return spans retain their source file. Generator methods and generator factories remain unresolved, because Pool does not consume their returned generator. String-named and dynamic callable selections remain explicit without retaining raw string values.

Literal pool member lists can contain a source `sendAsync` result or a constructed source class implementing `GuzzleHttp\Promise\PromiseInterface`. Promise consumption is separate from transport: consuming an existing promise never adds a second `uses-external-service` send. Inline asynchronous results require a verified source Saloon send at the exact source span; decoy methods remain unresolved. Transport metadata retains that span, and promise-consumption metadata states `prepares_another_send=false`. Callback candidates require possible request or promise members. Constructor payloads and resolved response values are omitted.

Members of literal lists can also be typed request variables or variables retaining the source origin of an earlier `sendAsync` result. Assignment aliases preserve that origin. The existing expression analysis evaluates keys and values once in source order and stores only member type descriptors and origin offsets. Reassignment, by-reference items and unresolved mutation do not retain a proved promise-consumption link. Two-item callable arrays remain separate from member lists. Origin lookup uses a per-file offset index rather than scanning every earlier send for each member.

Whole source member arrays can be assigned to variables and aliases before passing them to `pool`, a pool constructor, or `setRequests`. The expression evaluator retains bounded type and origin descriptors alongside the existing attachment descriptors, without array keys or scalar payloads. Reassignment to an empty list removes earlier candidates; unmodeled element mutation invalidates the retained list. The shared node and memory budgets also cover member evaluation.

Source factories returning member arrays can supply `pool`, a pool constructor or `setRequests`, directly or through variables and aliases. Factory selection checks source visibility, static invocation and abstract declarations, and follows nested source returns and inherited methods. Return-source evidence preserves the declaring file. Known list candidates remain conditional when another return cannot be resolved; generator return values do not become list members. Returned asynchronous promises use the factory file and original send span, so pool consumption never duplicates transport. Recursive return selection has a separate bounded resolver and reports its limit without suppressing unrelated pool candidates.

Source transport overrides, inaccessible or dynamic URL selectors, invalid argument shapes, missing source files and changed inputs remain explicit. String-named callback forms, returned pool factories, cross-callable mutations and explicit fluent `setConnector` selection are not yet composed by this integration. Source generator factories returning iterables and argument-dependent factory results remain unresolved.

## MCP tools

### architecture-search

Search uses a literal, case-insensitive fragment. Exact matches rank first. It can match names, paths, routes, tables, and element kinds. Select a candidate using its ID and source location before querying relationships.

| Parameter | Meaning | Default |
|---|---|---|
| `query` | Required non-empty literal fragment | None |
| `kind` | Exact element kind or role from `supported_kinds` | All |
| `path` | Relative file or directory prefix, matched on path segments | All |
| `limit` | Whole records per page, from 0 to 100; 0 returns a summary | 20 |
| `offset` | Zero-based page offset | 0 |
| `snapshot` | Previous response snapshot; required for later pages | None |

The result contains `candidates`. Multiple candidates require selection; an empty result does not authorize inventing a class name. The supported vocabulary lists available tags. Concrete shape coverage requires source evidence and its diagnostics.

### architecture-graph

| Parameter | Meaning | Default |
|---|---|---|
| `subject` | Required element ID, exact class name, or relative file path | None |
| `mode` | `context`, `path`, or `impact` | `context` |
| `target` | Destination selector, required only for `path` | None |
| `depth` | Maximum path or impact hops, from 1 to 20 | 4 |
| `limit` | Whole records per page, from 0 to 100 | 20 |
| `offset` | Zero-based page offset | 0 |
| `snapshot` | Previous response snapshot; required for later pages | None |

`context` returns incoming and outgoing direct relationships. `path` finds one shortest directed semantic path to the target. `impact` follows possible direct and indirect dependents and returns explanation paths. Structural containment does not imply that a class executes all of its methods.

## Example tool calls

Find a route:

```json
{"query":"billing.cancel","kind":"route"}
```

Use the returned candidate ID as `subject`. The placeholders below stand for IDs from actual search responses:

```json
{"subject":"<selected route ID>","mode":"context"}
```

Search for a service operation, select its candidate, and ask for a path from the route:

```json
{"query":"cancelInvoice"}
```

```json
{"subject":"<selected route ID>","mode":"path","target":"<selected method ID>","depth":12}
```

Before changing the method, inspect possible dependents:

```json
{"subject":"<selected method ID>","mode":"impact","depth":12}
```

A route-to-job path can distinguish dispatch from queued execution. Conditions such as registration, worker availability, and callback selection remain attached to the relevant transitions. A candidate test is a static connection to inspect or run; discovery provides no test execution or coverage result.

## Result interpretation

Inspect `status`, `analysis_complete`, `diagnostics`, `truncated`, and traversal budgets together.

| Field or status | Interpretation |
|---|---|
| `found` | The analyzed graph contains records matching the query |
| `ambiguous` | The selector needs a candidate choice |
| `not_found`, `empty`, or `no_path_in_analyzed_graph` | No matching evidence was found in the analyzed graph; inspect completeness before drawing a conclusion |
| `stale_snapshot` | Inputs changed; restart search or the first graph page |
| `unavailable` | Source inputs could not be read safely, or a traversal budget prevents a conclusive path answer |
| `analysis_complete: false` | Diagnostics prevent claiming complete coverage |
| `truncated: true` | The response omitted records; use `next` or narrow the selection |
| Counts with `lower_bound` | A traversal limit prevents an exact total |

Responses are limited to 65,536 bytes and retain whole records. Diagnostic details are selected for the current query and bounded; the summary can contain diagnostics whose details are absent. `next` carries continuation arguments. Preserve the snapshot for later pages. Do not combine pages from different snapshots.

Completeness describes the current inputs within the supported source contracts. Dynamic registrations, unsupported package releases, parse errors and reached budgets remain explicit diagnostics. A complete source graph does not prove runtime execution or cover every possible dynamic shape.

## Cache and measurement

Graph discovery reuses the existing per-file cache in `storage/framework/cache/architecture-kit`. Source statistics, file membership, graph configuration, and package source fingerprints invalidate affected entries. Memory guards can refuse a cache read or write and fall back to rebuilding.

Some partial results repeat for unchanged source. Diagnostics with `limit_reason: "structure"` retain source-bounded node, depth, or descriptor limits in cache. The warning remains in the reused result. Memory-dependent and unclassified limits are retried. Editing the source or changing the package fingerprint refreshes the facts.

The benchmark runs isolated synthetic projects with 1,000 and 10,000 PHP files and a copy of this package's `src`. It reports cold, warm, one-file-edit, and disabled-cache builds, query timings, payload sizes, memory, cache bytes, input hashes, and observed parser calls. It does not scan neighboring repositories.

```bash
php tests/Benchmarks/static-graph.php --sizes=1000,10000,repo --trials=5 --memory-limit=1024M --output=build/static-graph.json
```

The legacy context comparison uses the same inputs and machine. Expanded discovery has additional work; compare reported build and query costs for the relevant workflow. Failed gates remain failures and retain available measurement rows in the JSON report.

The five-trial local measurement on PHP 8.5.8/macOS used package source fingerprint `d60adeeb571c51f9a6c9ffe76ac90f20104ef3dc` and a 1024 MiB process limit. Build medians include file discovery/planning and graph building; catalog composition and queries are reported separately.

| Input | Cold build | Warm build | One-file edit |
|---|---:|---:|---:|
| 1,000 synthetic PHP files | 1,060 ms | 116 ms | 198 ms |
| 10,000 synthetic PHP files | 9,223 ms | 1,077 ms | 1,416 ms |
| Package source files | 16,471 ms | 393 ms | 645 ms |

All 120 isolated runs respected the parser gates: warm builds parsed zero files, one-file edits parsed one, and no file was parsed twice. The largest query payload was 60,094 bytes. Warm search/path/impact medians on 10,000 files were 62.02/75.27/0.72 ms. The warm graph used 452.4 MiB peak process memory and 47.6 MiB of disk cache. Warm build plus catalog composition medians were 281/2,719/1,031 ms for the three inputs respectively; query times are additional. These are local measurements, not production latency guarantees. Existing legacy-context query medians on unchanged synthetic inputs stayed within 0.95–1.07 times the preceding same-machine measurement; the broader catalog build is a separate workload.

Source test lifecycle links include PHPUnit `setUp`, `setUpBeforeClass`, `tearDown` and `tearDownAfterClass`, selected through source inheritance and traits for verified test methods. Inaccessible, abstract, wrong-static or required-argument hooks remain unresolved. Pest `beforeEach`/`beforeAll` are setup candidates and `afterEach`/`afterAll` are teardown candidates in the same source registration scope. Test execution and lifecycle selection remain conditional. Source-shadowed dataset registration functions do not prove a named dataset reference. PHPUnit `Before`, `BeforeClass`, `After`, `AfterClass`, `PreCondition` and `PostCondition` attributes select effective source methods through inheritance and trait resolution. Overrides without the hook attribute suppress inherited selection. The graph retains a literal priority, or marks the priority unresolved, without evaluating attribute arguments. Lookalike or source-shadowed attributes, incompatible declarations and invalid argument shapes do not prove a hook. Candidate selection is bounded and its limits are explicit. PHPUnit `DataProvider` and `DataProviderExternal` attributes select source methods through local inheritance or an explicit source class, including namespace imports. Providers must be public, static, concrete and have no parameters. The graph records a conditional test-data preparation link, attribute identity and the argument-count validation selector, while omitting dataset values. Missing, shadowed, dynamic or invalid provider declarations remain explicit. Global Pest hooks in inline `pest()` and `uses()` configuration chains link to source tests selected by literal relative file, directory or glob targets. Later `in()` calls replace the target selection; later hooks of the same kind replace earlier callbacks. `pest()` in `Pest.php` defaults to its directory, while `uses()` defaults to its source file. The graph matches indexed source paths without executing configuration or resolving filesystem globs. Dynamic targets, unsupported chain methods, invalid arguments, source API shadows and noninline callback selection remain unresolved. Generator hook bodies remain structural references because calling the hook does not consume the generator.

## Model tool-selection evals

The eval runner presents actual JSON-RPC `tools/list` definitions and server instructions from the current package and baseline commit `06c74c990408e960232ba07d2dfef2700094955c`. It uses synthetic tool responses for six tasks, with three trials per task and version. It records the model's actual calls and arguments, returned evidence, interpretation errors and source hashes. Synthetic resource-reading and verification tools are identified separately from package tools. A weather tool is an unrelated distractor.

The cases cover scaffolding, context before change impact, ambiguous route selection with pagination and a stale snapshot, event-to-job paths, guard findings with a doctor failure, and sequential Laravel AI upgrade guides. Found tests and dispatched jobs remain unexecuted. The runner does not edit application files.

Prepare both actual tool manifests without calling a model:

```bash
python3 tests/Evals/tool-selection/run.py
```

Preparation returns exit code 2 and an `OPEN` report. It does not count as a passed model eval. At the final verification stage, configure `EVAL_BASE_URL` with the OpenAI-compatible API base URL, `EVAL_MODEL`, and optional `EVAL_API_KEY` outside the repository, then run:

```bash
python3 tests/Evals/tool-selection/run.py --run --workers 3
```

The full run contains 36 trials. `--workers` allows one to three independent trials in parallel; each trial has its own synthetic tool state. New-text trials must satisfy all six cases. Baseline outcomes are reported separately, without a promised percentage improvement. An interrupted run remains `OPEN`. Model requests use the same reasoning, temperature and token budget for both versions. Set `EVAL_REASONING_EFFORT=medium` for OpenRouter reasoning models. This sends `reasoning.effort`, omits unsupported temperature, and increases the shared token budget from 2000 to 8000. The recorded report contains no API key. The API transport explicitly sets `strict: false` to preserve optional MCP parameters. A controlled OpenRouter probe showed that omitting this flag inserted an unwanted empty `target` in context mode. This flag does not change the exported MCP schemas or recorded model arguments.

Offline checks verify the evaluator's conversation loop, tool error handling, evidence use and rejection rules. Required source values must occur in actual tool replies and in the final answer or evidence strings, with token boundaries. A neighboring filename or invented evidence fails:

```bash
python3 tests/Evals/tool-selection/test_runner.py
bash tests/Evals/tool-selection/pest.sh harness
```

The Pest adapter uses `pestphp/pest-plugin-evals` 5.1.0 with Pest 5 in a temporary dependency directory. The optional host includes `illuminate/support` 13 for the Laravel helper functions used by plugin expectations. It requires PHP 8.4+ only for these optional eval checks and leaves the package's PHP and runtime dependencies unchanged. Its tool-call and trajectory scorers need no separate judge model. After the real model report is complete, validate it with the plugin:

```bash
EVAL_REPORT="$PWD/build/catalog-parent/tool-selection-report.json" \
EVAL_SCENARIOS="$PWD/tests/Evals/tool-selection/scenarios.json" \
bash tests/Evals/tool-selection/pest.sh report
```

A missing or incomplete report fails validation. Offline checks are harness tests, not proof that an AI chose the correct tools. Pest dependencies are installed only in the temporary directory and removed afterwards.
